Launch tasks

Everything left to launch 1on1 — written for a human, not a developer. The code side is done; these are the account-and-dashboard steps only you can do.

Do before launch Do at launch

1 · Rotate the keys that were shared in chat

Do before launch

Why: secrets pasted into chats should be treated as compromised. Rotating them takes ~10 minutes and closes the risk completely.

  1. Roll the Stripe secret key. Go to dashboard.stripe.com → Developers → API keys. Find the Secret key starting with sk_test_… and click the … menu → Roll secret key. A new key appears (it starts with sk_test_ too). Click to copy it.
  2. Roll the Stripe webhook secret. Still in Stripe: Developers → Webhooks. Click your endpoint (the one pointing at …supabase.co/functions/v1/stripe-webhook). On its detail page click Roll signing secret → confirm. Copy the new whsec_… value.
  3. Create a new Daily API key. Go to dashboard.daily.co → Developers (left sidebar) → API keys. Click + Create API key, name it 1on1-prod, copy the new key, then delete the old key from the list.
  4. Revoke the old Expo token. Go to expo.dev → log in → click your avatar → Access Tokens. Delete the old token. (No need to create a new one now — you'll be asked to log in again the next time a build is made.)
  5. Hand the three new values to your coding agent (paste them in chat). It will run supabase secrets set STRIPE_SECRET_KEY=… STRIPE_WEBHOOK_SIGNING_SECRET=… DAILY_API_KEY=…, redeploy the affected functions (create-payment-intent, stripe-webhook, create-video-session, cancel-booking), and re-run the payment and video checks to prove the new keys work.
Afterwards the app needs nothing — it uses the publishable key, which is public by design and doesn't rotate.

2 · Add a payment method to the Daily account

Do before launch

Why: without a card on file, Daily shows a "Missing payment method" screen instead of the video call — the app-side join flow itself already works.

  1. Log in at dashboard.daily.co.
  2. Click Billing in the left sidebar (you may need to pick your organization first, bottom-left).
  3. Click Add payment method (or "Upgrade plan" if it routes you through plan choice — the free tier is fine to start; a card is required either way).
  4. Enter the card details and save. Daily may show a $0 or $1 temporary authorization — that's normal.
  5. Test: create a paid booking in the app whose time window is open, tap the session → Join video lobby → Join session. The Daily prejoin page ("Ready to join?", mic/camera toggles) should load instead of the payment gate. Your coding agent can do this test with you on the emulator.

3 · Fill in the legal document placeholders

Do before store submission

Why: app-store reviewers read the Terms and Privacy Policy; bracketed placeholders look unfinished and can trigger rejection.

  1. Open the two source files: public/legal/terms-of-service.html and public/legal/privacy-policy.html in the 1on1 repo (any text editor).
  2. Search for PLACEHOLDER. You'll find: legal entity name (use the exact registered name, e.g. "DeepWorks LLC"), registered address, effective date, and governing jurisdiction (e.g. "the State of Delaware").
  3. Replace each highlighted field. Ideally have a lawyer skim both docs once — they're written to be honest and complete, but only counsel can give legal advice.
  4. Save both files, then ask the coding agent to publish (it runs sh scripts/publish-legal-site.sh "Fill legal placeholders"). The pages refresh on this site within a minute.
  5. Check: open deepworksllc.github.io/legal/terms-of-service.html — no more orange banner or brackets.

4 · Swap in Stripe LIVE keys

Do at launch

Why: everything so far ran in Stripe's test mode (fake cards like 4242). Real customers need live mode, where real cards are charged.

  1. In dashboard.stripe.com, find the toggle in the top-right that says Test mode and switch it off. The whole dashboard now shows live data.
  2. Developers → API keys → reveal and copy the Secret key (sk_live_…). Keep this one extra safe — it moves real money.
  3. Developers → Webhooks → + Add endpoint. URL: https://vaqibgoukmsrsptugrpp.supabase.co/functions/v1/stripe-webhook. Event: payment_intent.succeeded (add charge.refunded too if you plan in-dashboard refunds). Create it, then click Roll signing secret (or "reveal") and copy the whsec_….
  4. Copy the Publishable key (pk_live_…) from the API keys page as well.
  5. Give all three to the coding agent. It will set the secrets, redeploy functions, update the app config (.env + eas.json publishable key), and run one real-card smoke charge that you refund from the Stripe dashboard.
  6. Cleanup: in Test mode's webhook list, delete the old test endpoint if a duplicate was created during setup (the live endpoint is the one under the live-mode toggle).
Stripe live mode requires account activation (business details, bank account for payouts) — if you haven't completed that, the dashboard will prompt you at step 1. Allow a day or two for verification.

5 · Apple Pay merchant certificate

Do at launch (iOS)

Why: lets iPhone users pay with Apple Pay in addition to typed cards. Android/Google Pay is unaffected.

  1. You need an Apple Developer Program membership ($99/year) at developer.apple.com — enroll first if you haven't.
  2. In Apple's developer portal: Certificates, Identifiers & Profiles → Identifiers → + → choose Merchant IDs → description 1on1, identifier merchant.com.deepworks.oneonone → Register.
  3. In the Stripe dashboard: Settings → Payment method domains (or iOS Apple Pay certificate settings) → Add new application. Stripe gives you a CSR file to download.
  4. Back at Apple: open your merchant ID → Create Certificate → upload Stripe's CSR file → download the signed applepay.cer it gives you.
  5. Upload that .cer file back into the Stripe dashboard page from step 3. Apple Pay is now active for the domain.
  6. Tell the coding agent — the app already passes merchant.com.deepworks.oneonone at payment time; it just needs the certificate to exist (steps 2–5).

6 · Build & submit to the app stores

Do at launch

Why: the final step — producing the store packages and submitting them for review.

  1. Google Play (Android): create a developer account at play.google.com/console (one-time $25). Then have the coding agent run the production build (eas build --profile production --platform android) to get an .aab file, create the app in the Play Console, upload it, fill in the store listing (description, screenshots, the privacy-policy URL from this site), and submit for review. Review usually takes 1–7 days.
  2. Apple App Store (iOS): in appstoreconnect.apple.com create the app record (needs the bundle id com.deepworks.oneonone registered on your Apple account). The coding agent runs the iOS production build (eas build --profile production --platform ios — needs the Apple account connected), then submits via eas submit. Review typically takes 1–3 days. The privacy-policy URL and support contact come from this site.
  3. Both stores require: a support URL (use this site's Support page), a privacy-policy URL (/legal/privacy-policy.html), screenshots (the agent can capture them from the emulator), and a data-safety questionnaire — answers are already documented in the Privacy Policy: name + email, booking data, Stripe-processed payments, Daily video rooms, no tracking.

7 · Turn on error reporting (Sentry)

Do at launch

Why: when something breaks for a real user, you want to know immediately — not via a bad review.

  1. Create a free account at sentry.io → create a project → choose platform "React Native" → copy the DSN string it shows (looks like https://…@o….ingest.sentry.io/…).
  2. Paste it to the coding agent, who sets EXPO_PUBLIC_SENTRY_DSN in .env and eas.json. Error reporting is already wired in the app — it just needs the address to send to.

Blocked on a step? Hand it to your coding agent — anything inside the repo (builds, deploys, tests, configs) is automated; these pages list only what needs a human with dashboard access.
